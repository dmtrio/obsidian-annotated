# PLN — Vault Tools & Key Capability Tiers

> **Implementation status (2026-06-13): steps 1–5 built on branch `feat/vault-tools-key-tiers` — all 227 tests green, production build clean. Step 6 (live verification) pending deploy.** The new tools run on the branch, but the live MCP still serves v0.1.6, so end-to-end poll/additive/destructive verification against the real vault waits on reloading the plugin from this branch. One deviation from D9: move/delete keep the server thin (`notes.move`/`notes.trash` + cache invalidation) and reuse the existing `vault.on("rename")`/`on("delete")` handlers for sidecar coupling, rather than adding `CommentStore.moveComments` — the MCP server shares `commentManager.store`, so those handlers already keep its cache coherent.

> Close the read/navigation and structural-mutation gaps against a general-purpose vault MCP (the `mcp-obsidian` comparison, 2026-06-13) **without** giving up what makes this server different: identity-bound auth, the folder fence, and a server that imports no `obsidian` (everything through `NoteAccess`). Two coupled deliverables: a small set of new MCP tools (`list_notes`, `search_notes`, `read_multiple_notes`, `move_note`, `delete_note`) and the **capability ladder** that gates them — today's binary `full`/`watch` becomes an ordered `poll → additive → destructive`. The tools and the ladder ship together because the destructive tools must not exist without the tier that gates them.

---

## Purpose

An agent connected to this server today can only act on notes whose paths it was handed: there is no `search`, no directory listing, no batch read, and no way to move or remove a note. That's a real ceiling for the review workflow the plugin exists to serve — "find the notes that need attention" currently requires the human to name every file. `mcp-obsidian` (a general filesystem MCP that, notably, *writes this plugin's own `.comments.json` format*) has all of these; it lacks what we have — cryptographic identity on every write, the folder fence, the non-clobber temperament. The goal is to absorb its navigation surface while keeping ours the **system of record**.

Two of the new tools (`move_note`, `delete_note`) are the server's **first structural-mutation surface** — the first that can make a note disappear from where someone expects it. The existing `full`/`watch` split can't express "may edit but may not delete": `watch` reaches only the actionable GET, `full` reaches every tool. So the same plan introduces an **ordered capability ladder** — `poll ⊂ additive ⊂ destructive` — that the new (and existing) tools register against. This is the natural next axis after the folder fence: the fence answers *where*, the tier answers *what*.

**Definition of done**

- [ ] An agent can discover notes in scope without being handed paths: `list_notes` (fenced, recursive, flags which have comments) and `search_notes` (content + metadata, ranked) both exist and clamp to the key's fence.
- [ ] `read_multiple_notes` reads up to 10 notes in one call with partial success (`{ok, err}`), each path fence-checked independently.
- [ ] `move_note` and `delete_note` exist, are **trash-not-unlink** / **rename-not-overwrite**, and carry the note's `.comments.json` sidecar with them (rename + `note_path` rewrite on move, trash on delete) so no comment thread is ever stranded or orphaned.
- [ ] `KeyScope` is an ordered ladder `poll | additive | destructive` (room for `admin` later); each MCP tool declares a `minTier` and is **conditionally registered** — a tier that can't use a tool never sees it in its tool list (loud-by-absence, not 403-on-call).
- [ ] Migration is conservative: existing `watch` keys → `poll`, existing `full` keys → `additive`. **No key silently gains delete.**
- [ ] The settings UI mints capability with two buttons — *Create Read/Write* and *Create Read/Write/Move/Delete* — each issuing a `poll` + write-tier **pair**, so the always-on watcher token stays read-only even when the agent can write.
- [ ] The whole server still imports no `obsidian`: every new capability is a `NoteAccess` (or `CommentStore`) method, fake-able in node; tool handlers stay tested in `tests/mcp/`.

## Decisions

- **D1 — `KeyScope` becomes an ordered ladder; names are abstract internally, descriptive in the UI.** Replace the binary `full | watch` with `poll | additive | destructive` (extensible — `admin` is the obvious fourth). The internal identifier is **abstract on purpose**: the scope string is *persisted* (device `localStorage` keys, the `ANNOTATED_MCP_KEYS` env JSON), so it is a stable id, and a stable id must not enumerate its current verbs — the verb set drifts. The `poll` tier already grew from "read the actionable feed" to also cover `read_note`/`search`/`list`; `destructive` will grow (an `archive` someday). An internal value literally named `move-delete` would be a lie the moment the third destructive verb lands, and it lives in everyone's stored keys where it can't be cheaply migrated. So: **abstract internal, literal UI.**
  - **Internal → UI mapping:** `poll` → "Read", `additive` → "Read + Write", `destructive` → "Read + Write + Move/Delete". The UI is free to be a capability list because it is not persisted and re-renders from the live enum.
  - **`poll` vs `read`:** `poll` describes the watcher use-case, `read` the capability; since the tier now grants general reads, `read` is marginally more accurate, but `poll` is chosen for continuity with the watch surface and because, being abstract, it ages fine either way. (Settled, not re-litigated.)

- **D2 — The tier boundary is "can a note vanish or be clobbered", and that puts both `move` and `delete` in `destructive`.** The line between `additive` and `destructive` is **not** "loses data" — it is *can this affect a note other than by adding content / can it overwrite a second file*. `additive` means: only ever appends content or edits a single named note in place; it can never relocate, remove, or touch a second file. That is a tier you can hand an agent without thinking. `move_note` fails the test twice — it makes the note disappear from its old path (which is why it must drag the sidecar) and rename-onto-existing is an overwrite — so it sits with `delete_note`, not in `additive`. Reversibility (move is undoable, delete-to-trash is recoverable) is irrelevant to tiering: both are the same "rearrange the vault" power, so they share a gate.

- **D3 — Tools are gated by *conditional registration*, not runtime refusal.** `buildMcpServer` already receives the authenticated `key` (it's how `assertPath` works). Each tool declares a `minTier`; the server registers only the tools the key's tier reaches. A `poll` key's `tools/list` simply does not contain `add_comment` — the capability is absent, not present-and-throwing. This matches the server's existing "loud, not silently-empty" principle (cf. `resolveQueryScope` refusing rather than returning empty) and is clean because each bearer key is one client connection, so per-key tool lists never collide. The HTTP actionable surfaces keep their own gate (`canAccess`, refactored to `tier >= poll`).

- **D4 — Migration maps `watch → poll`, `full → additive`, never to `destructive`.** Existing `full` keys have never been able to delete (the tools don't exist yet). Mapping `full → destructive` would silently arm every key already sitting in someone's storage the instant this ships. Mapping `full → additive` preserves exactly today's real capability (read + write, no structural mutation) and makes `destructive` a **new tier nobody holds until they deliberately re-mint**. The mapping is applied at read time in the auth layer so stored `"full"`/`"watch"` strings keep working without a storage rewrite.

- **D5 — Minting issues a `poll` + write-tier *pair*; two buttons choose the write tier.** Today `mintPair` issues `full` + `watch` together under one `pairId` precisely so the token in a 24/7 monitor loop is read-only and can't write if it leaks. Keep that property: each create action mints `poll` + one write tier.
  - **Create Read/Write** → `{ poll, additive }` (shared `pairId`).
  - **Create Read/Write/Move/Delete** → `{ poll, destructive }` (shared `pairId`).
  The poller always uses the `poll` token; the agent uses the write token. This also answers the earlier "mint all three?" — **no**: a button mints `poll` + exactly one write tier, so the dangerous `destructive` token is only ever manufactured by the explicitly-scarier button, never sitting in storage by default. A **read-only watcher needs no separate button** — it just uses the `poll` half of any pair and discards the write half. Revocation stays pair-level (`revokePair`), unchanged.

- **D6 — `search_notes` uses Obsidian's ranking *primitives*, not its search *pane*, behind an optional `NoteAccess.search` hook.** The search pane (`internalPlugins … global-search`) is private/unsupported — out. What is public and worth using: `prepareSimpleSearch`/`prepareFuzzySearch` (the scorer behind the pane, pure functions returning `{score, matches:[start,end][]}` — ranking *and* highlight offsets for free), `vault.cachedRead` (warm read, not cold disk), and `metadataCache.getFileCache` (titles/headings/tags/frontmatter with **no** file read). Content search still reads bodies — there is no public full-text index to borrow — so the win over a naïve grep is read-warmth and ranking *quality*, not avoiding reads.
  - **Seam:** `search?(query, scopes, opts): Promise<Hit[]>` is **optional** on `NoteAccess`, absent ⇒ tool returns `[]` — the exact pattern `listFrontmatter` already uses. The bridge implements it with the Obsidian primitives; node tests inject a trivial `indexOf` scorer. Ranking quality lives untested in the bridge (it's Obsidian's code), the tool handler stays tested. Fence applied via `resolveQueryScope` before scoring.

- **D7 — `list_notes` is recursive, fenced, and folds in the comment flag.** Add `listPaths(): Promise<string[]>` to `NoteAccess` (the third `vault.getFiles()` consumer alongside `listCommentedNotePaths`/`listFrontmatter`). The tool clamps with `resolveQueryScope` + `pathInScope` (mirrors `check_frontmatter` line-for-line) and returns `[{ path, hasComments }]` by intersecting with the already-cheap `listCommentedNotePaths()` set — a recursive "what's here and what already has threads", which is the question the review agent actually asks, not a one-level `dirs[]`/`files[]` dump.

- **D8 — `read_multiple_notes` is pure composition; no new plumbing.** Loop `notes.read()` + `assertPath` per path, push fence-misses / not-founds to `err[]` instead of aborting, cap at 10, return `{ok:[…], err:[…]}`. No `NoteAccess` change at all — the cheapest item in the set, and it depends on nothing but the tier gate.

- **D9 — `move`/`delete` couple the sidecar through `CommentStore`, and trash beats unlink.** This is the only genuinely new infrastructure, and it exists because the `.comments.json` sidecar must travel with its note or the plugin's whole value prop breaks.
  - **Delete:** `delete_note` trashes the note **and** its sidecar via `vault.trash` (respecting Obsidian's configured "Deleted files" behavior — system trash vs vault `.trash/`), never `adapter.remove`. Both recoverable, recoverable *together*.
  - **Move:** `move_note` renames the note with `app.fileManager.renameFile` (so vault-wide wikilinks/backlinks get rewritten — `adapter.rename` wouldn't), then renames the sidecar to match and rewrites the `note_path` field inside the `CommentFile`. Routed through new `CommentStore.moveComments(old, new)` / `deleteComments(path)` so the store's **path-keyed in-memory cache is invalidated/rekeyed** — a raw bridge rename would leave the cache stale. `buildNoteAccess` gains `app`/`fileManager` (it currently only closes over `vault`); `NoteAccess` gains `trash(path)` and `move(old, new)`.
  - **Fence both ends:** `move_note` calls `assertPath` on source *and* destination; either outside the fence ⇒ loud refusal. `delete_note` fences its one path.
  - **`confirmPath` is dropped.** With a real `destructive` tier gating the tool *and* trash making it recoverable, the mcp-obsidian-style `confirmPath` echo is redundant belt-and-suspenders; leave it out to keep the signatures clean. (Re-add only on `delete_note` if a real incident argues for it.)

## Plan

> One commit per step in `obsidian-Annotated`. Builds on the note-write tools (v0.1.5: `create_note`/`append_note`/`patch_note`) and the identity/fence model already shipped. The tier refactor lands **first** so the new tools have a gate to register against; destructive tools land **last** so the riskiest surface ships only once the ladder and the read tools are proven.

1. **Capability ladder (comments-core + server).** `KeyScope = "poll" | "additive" | "destructive"` as an ordered enum (`TIER_ORDER`); refactor `canAccess` to `tier >= required`; add a `minTier` to each tool's metadata and make `buildMcpServer` register conditionally on `key.scope`; apply the `watch→poll` / `full→additive` read-time migration in the auth layer (D1/D2/D3/D4). No new tools yet — re-tier the existing twelve. *Accept: unit tests — a `poll` key's tool list excludes every write tool and includes the reads; an `additive` key excludes `move`/`delete` (registered as no-ops here until step 4) but includes the writes; a stored `"full"` string authenticates as `additive`; `"watch"` as `poll`; the actionable GET still answers for `poll`.*

2. **Read-tier tools: `list_notes` + `read_multiple_notes` (D7/D8).** Add `NoteAccess.listPaths`; implement `list_notes` (fenced, recursive, `hasComments` via `listCommentedNotePaths`) and `read_multiple_notes` (pure composition, partial success, cap 10). Both `minTier: poll`. *Accept: `list_notes` returns only in-fence paths with correct comment flags; `read_multiple_notes` returns `{ok,err}` with an out-of-fence path landing in `err` while siblings succeed; over HTTP with a `poll` key.*

3. **`search_notes` (D6).** Optional `NoteAccess.search` seam (absent ⇒ `[]`); bridge impl with `prepareSimpleSearch` + `cachedRead` + `metadataCache`; fence via `resolveQueryScope`; node test with an injected `indexOf` scorer. `minTier: poll`. *Accept: query returns ranked hits with excerpt + line, clamped to the fence; a key fenced to `A/` never sees a match in `B/`; tool returns `[]` (not error) when the seam is absent; HTTP auth matrix reuses the read-tool shape.*

4. **Destructive-tier tools: `move_note` + `delete_note` (D2/D9).** `CommentStore.moveComments`/`deleteComments` (rekey cache + rewrite `note_path`); `NoteAccess.trash`/`move`; `buildNoteAccess` gains `app`; tools fence both ends, `minTier: destructive`. Trash respects Obsidian's deleted-files setting. *Accept: move relocates note **and** sidecar, rewrites `note_path`, rewrites a backlink in a third note, and a subsequent `read_comments` on the new path returns the threads; delete trashes both files recoverably; both refuse out-of-fence and are absent from an `additive` key's tool list; cache shows no stale path after move.*

5. **Settings UI: two-button paired minting + tier display (D5).** Replace the single create action with *Create Read/Write* (`poll`+`additive`) and *Create Read/Write/Move/Delete* (`poll`+`destructive`); show each key's tier with its descriptive label; revocation stays pair-level. *Accept: each button mints a pair under one `pairId`; the key list shows "Read", "Read + Write", "Read + Write + Move/Delete"; revoking a pair removes both halves; a minted `poll` token can drive the monitor but not write.*

6. **Live verification + docs.** On the container + Mac: a `poll` key searches/lists/batch-reads but cannot write; an `additive` key comments/edits but `move`/`delete` are absent; a `destructive` key moves a commented note (threads follow) and trashes one (recoverable). Update README + the parent LOG; note the `mcp-obsidian` parity reached. *Accept: DoD demonstrated live across all three tiers.*

## Open questions (for ratification / surfacing during build)

- **Actor attribution on destructive ops.** Writes stamp identity (provenance PLN); a `trash`/`move` currently records *who* nowhere. Probably acceptable (trash is recoverable, move rewrites links visibly), but if delete-attribution matters it wants a home — a `.trash` log line, or a provenance stamp on the moved note. Defaulting to **not recorded** for v1; surface if it bites.
- **`search_notes` ranking knobs.** `prepareSimpleSearch` vs `prepareFuzzySearch`, and whether to expose a metadata-only fast path (tags/headings without body reads) for large vaults. Settle in step 3 against the real vault (~248 notes), don't pre-build.
- **`admin` tier.** Named here as the ladder's headroom (key management, config writes, identity ops over MCP) but **out of scope** — no tool needs it yet. Recorded so the enum is built ordered, not so it's implemented.
- **A bulk/`move`-batch surface.** Deferred on the same principle as the frontmatter PLN's bulk-write: one move per call until call volume demonstrably hurts.

## Risks / notes

- **Stranded sidecars are the headline risk** — a `move`/`delete` that touches the note but not its `.comments.json` orphans threads, defeating the plugin's purpose. D9 routes both through `CommentStore` for exactly this; the step-4 accept test (threads survive a move, by reading them at the *new* path) is the guard, not an afterthought.
- **Cache coherence on move.** `CommentStore` keys by path; a rename without rekey returns stale/empty comments. The store methods must invalidate, and the test must assert no stale read — this is the `metadataCache`-vs-disk lesson from the watch PLN applied to the comment cache.
- **Search reads bodies.** No public full-text index exists; `search_notes` is O(in-fence notes) per call, `cachedRead`-warmed. Fine at vault scale today; the optional seam means a future stdio host (no `metadataCache`) can fall back to disk parse or simply return `[]`, same injected-source discipline as `listFrontmatter`.
- **`fileManager.renameFile` is plugin-host-only.** Like `metadataCache`, it lives behind the Obsidian bridge; a future stdio host implements `NoteAccess.move` by hand (rename + manual sidecar move, no backlink rewrite). Keep the capability on the injected interface, not in the server, so both hosts satisfy it — the same boundary that keeps the server `obsidian`-free.
- **Migration is read-time, not a rewrite.** `full`/`watch` strings stay in storage and map on load. A later storage normalization (rewriting them to `additive`/`poll`) is a separate one-shot, not required for correctness — noted so the mapping isn't mistaken for a blocker.
- **Two-writer reality, unchanged.** A human moving/deleting a note in the Obsidian UI while an agent edits it is last-write-wins / sync-mediated, exactly as comments and provenance already are; no new concurrency surface, just a new verb on the same single-writer path.
